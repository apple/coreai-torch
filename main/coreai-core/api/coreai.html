coreai¶

CoreAI high-level Python API.

The supported public API lives in two packages:

  • coreai.authoring — build AI Models programmatically.

  • coreai.runtime — load and run .aimodel files.

The raw MLIR Python bindings stay reachable under coreai._compiler (notably coreai._compiler.ir) as an escape hatch for power users, but they carry no stability guarantee and are unversioned: they track the LLVM pin and may change with any bump. Prefer the coreai.authoring facades, whose surface is versioned independently of that pin.

The type of scalars in the array.

classmethod from_descriptor(descriptor: NDArrayDescriptor) → Self¶

Allocates an NDArray from an NDArrayDescriptor.

Will have the correct shape, dtype, and alignment.

numpy() → ndarray[Any, Any]¶

Return the array as a NumPy array.

Standard dtypes (e.g. float32, int8) return a zero-copy view that shares the backing buffer and preserves strides via DLPack. For bfloat16 / float8 dtypes, which DLPack may not support depending on the NumPy version, it falls back to the buffer protocol: C-contiguous arrays return a zero-copy view, non-contiguous arrays (e.g. a transpose) return a copy gathered in C order. Sub-byte dtypes (int2, int4, …) are always unpacked into a new array.

property shape: tuple[int, ...]¶

The shape of the array.

property strides: tuple[int, ...]¶

The strides, in elements (not bytes).

Describes the distance, in elements, between consecutive values along a given dimension.

coreai.authoring¶

Authoring facades for CoreAI.

Everything in __all__ is the supported, versioned public surface: facade objects that accept and return other facades, never raw MLIR bindings. The raw MLIR Python bindings stay reachable under coreai._compiler.ir, but that path is unsupported and unversioned (see coreai).

final class coreai.authoring.AIModelAsset¶

A model asset.

Represents an unspecialized source model asset on disk. Unlike a loaded AIModel, an asset cannot be used directly for inference — it is used to query model information such as function signatures, metadata, storage/compute types, and to manage derived compilation artifacts. The asset is a directory (typically with an .aimodel extension) that contains an unspecialized model asset, along with any associated metadata.

executable(specialization_options: SpecializationOptions | None = None) → AsyncGenerator[AIModel]¶

Async context manager that loads this asset as a runnable AIModel.

Loads the model on entry and releases its resources on exit. Use this instead of constructing an AIModel directly to ensure the model lifetime is scoped to the block:

async with asset.executable() as model:
    outputs = await model.run(inputs)
Args:
specialization_options: Optional specialization options for model

compilation. Only available on macOS.

Yields:

AIModel: A loaded model ready for inference.

static is_valid(path: Path | str) → bool¶

Return True if the path contains a valid model asset.

Checks that the path is an existing directory with a known model extension and that it contains either a source program or a derived artifact.

The asset metadata, loaded from metadata.json.

The file-system path to the asset directory.

Return an in-memory representation of the on-disk IR bytecode.

summary(*, include_statistics: bool = True) → AIModelAssetSummary | None¶

Return a summary of the model’s source program.

Args:

types, and the operation distribution. This is considerably slower for large models. When False, only the function signatures are populated.

Returns:

An AIModelAssetSummary, or None if no source bytecode exists.

Raises:

update_metadata(updates: Callable[[AIModelAssetMetadata], None]) → None¶

Update the asset metadata atomically.

Calls updates with the current AIModelAssetMetadata object, which must be mutated in-place. Changes are written to metadata.json after the callable returns.

Warning

The callback must mutate the object it receives, not reassign the local variable. Reassigning is silently ignored:

# WRONG — reassignment has no effect; the update is lost
def update(m):
    m = AIModelAssetMetadata()   # rebinds local 'm', does nothing

# CORRECT — mutate the received object in-place
def update(m):
    m.author = "Alice"
Args:
updates: A callable that receives the current metadata and mutates it

in-place. Example:

asset.update_metadata(lambda m: setattr(m, "author", "Alice"))
Raises:

RuntimeError: If the updated metadata cannot be written to disk.

set_hardware_constraints(entrypoint: str, hw_constraint_config: dict[str, HardwareConstraints]) → None¶

Rewrite the named entrypoint with harware constraints on the specified IO.

Args:
entrypointstr

Name of the coreai.graph to rewrite.

hw_constraint_configdict[str, HardwareConstraints]

Mapping of tensor name → hardware constraints to apply. Names not present in the dict are left with their original types.

set_static_shape_config(entrypoint: str, shapes_config: dict[str, dict[str, tuple[int, ...]]]) → None¶

Specialize a graph into one statically-shaped entrypoint per configuration.

Each input named in shapes_config receives a coreai.enumerated_shapes attribute, then the pre-compilation rewrite runs and consumes it: the original dynamic graph is erased and replaced by one statically-shaped clone per configuration key, named <entrypoint>_<key>. Existing argument attributes — including coreai.name and any hardware-constraint encoding on the argument type — are carried over to every clone.

Warning

entrypoint no longer exists once this returns. Later calls that name it — including a second call to this method — raise, because only the <entrypoint>_<key> graphs remain. set_hardware_constraints may be applied either before or after this method, but afterwards it has to name the generated graphs.

Parameters¶

entrypointstr

Name of the coreai.graph to specialize.

shapes_configdict[str, dict[str, tuple[int, …]]]

Mapping of new entrypoint name → (input name → static shape). Inputs not mentioned in any entrypoint dict keep their original type in every specialization.

class coreai.authoring.DType¶

numpy.dtype-like facade over an MLIR scalar type.

A dtype pairs the deferred MLIR-type thunk (inherited from Type) with its canonical MLIR name and an optional numpy dtype. Instances are the pre-registered module singletons; direct construction is disallowed (inherited from IRObject) — use e.g. float32.

Equality and hashing come from ValueEquality keyed on _eq_key (the canonical name), so they never require an active Context.

property numpy: np.dtype[Any] | None¶

The corresponding numpy dtype, or None (e.g. for index).

class coreai.authoring.HardwareConstraints(allocation_type: AllocationType, alignments: tuple[int, ...], interleave: tuple[int, ...])¶

Hardware constraints tensor-encoding attribute (a frozen IRObject).

Describes hardware-specific layout requirements — the backing allocation (allocation_type) plus per-dimension alignments and interleave. Frozen so it is hashable and participates in TensorType’s equality key.

class coreai.authoring.ImageConstraints(backing: ContainerType, row_alignments_per_plane: tuple[int, ...], *, four_cc: FourCC | None = None)¶

Image encoding tensor-encoding attribute (a frozen IRObject).

Carries the backing buffer type (CVPixelBuffer/MTLTexture) and the minimum row_alignments_per_plane for each plane of the image.

four_cc is an optional, keyword-only authoring sidecar kept for backward compatibility: it is not carried by the #coreaix.image_constraints attribute — the CoreAI ImageType carries the FourCC separately — so it is excluded from equality/hashing (compare=False) and is not recovered by _from_mlir(). It is keyword-only so the two serialized fields stay the positional interface.

final class coreai.authoring.Module¶

A CoreAI authoring module that holds the IR being constructed.

  • Create a Module with Module.create(); a default context and source-line location are bootstrapped for you.

  • Use the Module as a context manager to append operations to the module body. On a clean exit from the with block, the frontend-agnostic pre-compilation rewrite passes are applied to the IR in place.

  • Inspect the constructed IR with verify, dump, and as_string.

The rewrite passes run over the whole module on each clean exit, so building a module across several with blocks re-optimizes it once per block. A handle obtained inside a block survives only if the rewrite keeps its operation — reading one that was folded or DCE’d away is a use-after-free, and will crash rather than raise.

as_string() → str¶

Return the IR as a string.

Create a Module.

Bootstraps a context and an active location if they do not exist.

The location where the Module was created, as a DebugInfo facade.

dump() → None¶

Print the IR to stderr (useful for debugging).

Verify the constructed IR for correctness. Raises on error.

class coreai.authoring.SubprogramScope(name: str, file: FileInfo, compile_unit: CompileUnitScope | str, linkage_name: str = '', mlir_type_str: str | None = None)¶

A DWARF subprogram (function) scope.

compile_unit is either a full CompileUnitScope or a bare symbol name referencing one. mlir_type_str is the subprogram’s MLIR function type as a context-free textual spelling, re-parsed under a Context in DebugInfo._to_mlir(); it is excluded from equality (compare=False) because it is a context-bound implementation detail, not identity.

class coreai.authoring.SymbolRefScope(symbol: str)¶

A bare @symbol reference to a scope (symbol stored without @).

symbol must be a valid MLIR bare identifier (no spaces or characters that would require @"..." quoting, and no nested a::b path): it is emitted and recovered via @-prefixed string spelling, matching the incumbent authoring builders. Op/graph/func names are Python identifiers, so this always holds for the locations authoring produces.

class coreai.authoring.TensorType(shape: Sequence[int] | None = None, dtype: _DTypeLike | None = None, name: str | None = None, encoding: _Encoding | None = None)¶

The tensor shape, or None when unmaterialized.

class coreai.authoring.Type¶

Abstract base facade for all MLIR types.

The deferred-construction thunk in _inner lets a facade be created (e.g. a module-level dtype singleton) without an active MLIR Context; the thunk is only invoked by _to_mlir(), which must run with a Context active on the current thread. Concrete subclasses populate _inner via _make().

Type is never instantiated directly: it does not implement __str__(), so it remains abstract and _make raises for it. Concrete subclasses supply __str__ and register themselves in TYPE_REGISTRY so _from_mlir() can route to them.

TanhOp constructor.

Applies element-wise hyperbolic tangent to the input tensor.

Computes tanh(x) = (e^x - e^(-x)) / (e^x + e^(-x)) for each element. The domain is all real numbers and the output range is (-1, 1). Follows IEEE 754 semantics: tanh(0.0)=0.0, tanh(-x)=-tanh(x) (odd function), tanh(+inf)=1.0, tanh(-inf)=-1.0, tanh(NaN)=NaN.
